# 11 M3 交付说明（联机模式：服务端 + 账号 + 网页管理端）

> 形态：`aoc-server`（FastAPI + SQLAlchemy + PostgreSQL/SQLite）为公司与运营数据权威；桌面客户端通过 Bearer 令牌接入，管理员通过独立 SPA（Cookie + CSRF）管理；个人模式（M1）与单机运营（M2）保持完全离线可用。

## 2. 形态与进程

```
浏览器（apps/admin-web，/admin）
  │ 静态资源 + JSON（Cookie + X-CSRF-Token）
  ▼
aoc-server（FastAPI，/api/v1）
  ├─ /auth/*           玩家 Bearer（access + refresh）
  ├─ /flights、/roster、/sync …  玩家/客户端
  ├─ /admin/auth/*     管理端会话
  ├─ /admin/*          管理端 JSON（逐路由角色校验）
  └─ SQLAlchemy → PostgreSQL 16（部署）/ SQLite（开发、测试）
        ▲
        │ HTTPS + Bearer
桌面客户端（Tauri + React）── /ops/online ── 登录、抽班、同步状态
        └─ aoc-core（本地 sidecar）+ SimLink（M1/M2 链路保持原样）
```

- 服务端只返回 JSON；`/admin/*` 的 SPA fallback 只用于把 `index.html` 返回给浏览器（`W-A11/W-A12`）。
- 同一进程同时承载 `/api/v1` 与 `/admin` 静态资源，默认同域，不需要 CORS；开发用 Vite 代理。

## 3. 实现范围

### 3.1 账号、公司与权限

- 公司：名称/ICAO/呼号前缀/基地/货币/初始资金/余额/时区/简介；货币创建后只读（MVP 不做汇率），ICAO 只读。
- 角色：`ADMIN` / `DISPATCHER` / `PILOT`；管理端只允许前两者登录，PILOT 登录返回 403。
- 邀请码：角色、次数、有效期；`POST /auth/register` 注册即用掉一次。
- 玩家令牌：HMAC-SHA256 签名的 access token（默认 120min）+ 数据库存储哈希的 refresh token（默认 30 天，刷新即轮换）。
- 管理端会话：随机 256-bit 会话串，DB 只存 SHA-256；Cookie `HttpOnly`、`SameSite=Lax`、`Secure` 可配；空闲 30min、绝对 12h；每会话独立 CSRF token，所有非 GET 请求校验 `X-CSRF-Token`。
- 密码：`hashlib.scrypt`（n=2^14, r=8, p=1；不引入额外原生依赖，Argon2id 可在部署镜像替换）；最少 8 位。
- 登录限流：进程内按 `IP+用户名` 5 次/5 分钟；失败不区分用户不存在/密码错误。
- 审计：登录/登出/配置发布/回滚/用户/邀请码/机队/机票/航线/班期/强制释放/复核/资金调整写 `audit_log`，含 before/after、原因、IP、User-Agent、request_id。

### 3.2 运营数据（服务端权威）

- 机场库：内置 23 个常用机场（含大小/需求/等级）；`/admin/network/airports` 可查。
- 机型模板：从 `data/aircraft_types.json` 补全为运营机型（含 `A343/BIZJET`、`C25C/BIZJET`），支持自定义。
- 机队：注册号、机型、基地、当前位置、状态、引进方式、租赁/小时、总小时/循环、油量；并发锁见 §3.4。
- 航线/班期/航班实例：商业航线（距离/block 可自动算）→ 班期模板（本地时刻、星期、有效期、机型）→ 按天生成航班实例（时区走 `zoneinfo`，UTC 落库）；支持 CSV 导入（逐行 savepoint，错误行号返回）。
- 抽班：`POST /roster/draw`，支持指定 `flight_ids` 或按飞机当前位置自动串 1–6 段；写 `roster` + `roster_leg` + `aircraft_lock`；同一账号只允许一个 `ACTIVE` 班表。
- 配载：`GET /flights/{id}/loadsheet`，复用 M2 `aoc_core.ops.economy.generate_load_sheet`（AIRLINER/BIZJET/VIP/CARGO 分支、重量削减），开始航班时固化 `economy_snapshot`。
- 结算：落地时用实际航时/油耗重算收入与成本，套用**开始时的策略快照**；`ACCEPT/WEIGHTED/REVIEW/REJECT`、`reject_cost_mode`、`review_advance_ratio` 全部生效；复核 `WEIGHTED` 可手填因子；`NONE` + `REJECT` 记 `VOID` 不写账本。
- 账本：只追加，逐条 `balance_after`；预付款先入账，复核完成写 `ADVANCE_RECOUP` 冲回；飞行员只能看到自己的账本，公司账本在管理端概览。
- 飞行员覆盖（A-20）：`scope_mode=ALLOW_OVERRIDES` 时覆盖优先级 **飞行员 > 单机 > 机型 > 公司**；额度、规则与 M2 相同。
- 版本化配置：`公司配置版本` + `company_setting_history`；发布用 `expected_version` 乐观锁，冲突返回 `CONFIG_VERSION_CONFLICT`；回滚生成新版本，不删除历史；发布/回滚都写审计并发 `CONFIG_CHANGED` 同步事件。

### 3.3 同步与离线补传

| 能力 | 实现 |
|---|---|
| 增量轮询 | `GET /api/v1/sync?cursor=` → `{cursor, has_more, server_time, events, company, config_versions}` |
| 幂等写 | 玩家写操作支持 `Idempotency-Key`；`idempotency_key` 按 `(company,user,key)` 唯一，重复请求回放原响应 |
| 离线 outbox | `POST /api/v1/sync/batch`，逐条 `savepoint`：单条失败不影响整批；支持 `START/LOADSHEET/TRACK/LANDING/ABANDON/HEARTBEAT`；返回每条 `ok/duplicate/error` 与 `retryable` |
| 轨迹补传 | `track_chunk` 按 `(flight_id, seq)` 唯一，重复 seq 计 `duplicates`，不重复写 |
| 锁心跳 | `POST /locks/{id}/heartbeat`：在飞 6h、待飞 1h 续期；过期锁由抽班前惰性回收，把航班放回 `SCHEDULED` |

### 3.4 并发

- 抽班事务内先检查飞机活动锁，再插入 `aircraft_lock`；`aircraft_lock` 对 `(company_id, aircraft_id)` 建有 `status='ACTIVE'` 的**部分唯一索引**（SQLite/PostgreSQL 均生效），并发时只有一个事务成功。
- SQLite 开发/测试使用 WAL + `BEGIN IMMEDIATE`（写事务串行化）+ 30s busy timeout；PostgreSQL 使用 `SELECT … FOR UPDATE SKIP LOCKED` 选飞机。
- 测试：两位飞行员、同一架飞机、两个不同航班并发抽班，结果稳定为 `200 + 409`，活动锁恰好 1 个。

## 7. 已知限制与后续（M3.1 / M4）

1. **客户端联机链路是「登记 + 同步」而非完整权威飞行**：`/ops/online` 已支持登录、看服务端航班、抽班、看当前班表、锁心跳与增量同步；但 SimLink 录制、配载、落地仍走 M2 本机 `aoc-core`。服务端的 `start/loadsheet/track/landing` 已实现并通过冒烟，客户端尚未把 SimLink 事件自动上报服务端。M3.1 需要把 `FlightService` 的 `on_finalized` 钩子接到 outbox → `/sync/batch`。
2. **M2 本地数据一次性导入未实现**：新服务端从空库建公司/管理员；M2 机队/航线/班期/结算迁移脚本待补。
3. **CPDLC / Hoppie 上行报文未实现**（D-26/D-27，属 P1）。
4. **遥测反作弊仍以客户端上报为准**：服务端做策略折算与复核，但未做轨迹包线/瞬移/加速的服务端二次校验与 HMAC 遥测签名。
5. **单公司**：一个服务端一家公司；无跨公司超管、无多租户切换。
6. **管理端覆盖编辑**：飞行员/机型/单机覆盖可通过策略 JSON 的 `overrides` 配置，尚未做三 Tab 表单；航点/公司航路有 API 但未单独出页面。
7. **限流为单进程内存**：多 worker/多实例部署需换 Redis 或网关限流；管理端 IP 白名单与 2FA 由部署层/后续补。
8. **Alembic 基线是整库建表**：后续表结构变更需拆成增量迁移；本地只验证了 SQLite，PostgreSQL 需在 CI 容器中补跑。
9. **管理端产物未做路由级 code split**：单包 gzip 约 392KB，满足 500KB 目标但可继续拆分。
10. **管理端 UI 冒烟覆盖范围有限**：已覆盖登录与 10 个页面渲染/接口加载，尚未覆盖表单提交、配置发布、复核等交互流程。

## 8. 回滚
