# 04 班表与经济规则

> 版本 v0.1 · 状态：建议方案（待评审）
>
> 本文所有数值都是**初始默认值**，用于跑通与校准，不是最终平衡值。所有参数必须可在管理端修改，并按航班快照。
>
> 里程碑：M2 单机运营模式下，本文的「服务端」由 `aoc-core` 本地承担，参数在客户端「运营规则」页修改；「管理员/复核」由本人在客户端复核队列完成；飞行员覆盖不适用（M3 再加入）。这些替换不改变公式与验收口径。

## 1. 设计目标

1. **可解释**：玩家能看到为什么抽到这组班、为什么赚/亏。
2. **可调参**：经济参数集中管理，改完下一班生效，不写死在代码里。
3. **防刷**：不能靠短途往返、时间加速、伪造数据来无限刷钱；重抽不产生收益，只有飞完才结算。
4. **单人可玩**：一个人也能开公司、抽班、飞、结算；多人只是共享同一套规则。
5. **失败有代价，但不劝退**：取消/备降/坠机有成本，不直接删号。

## 2. 班表模型

### 2.1 三层结构

```
航线 Route（ZBAA–ZSSS，距离、预计航时、最低机型）
  └─ 班期模板 Schedule（AOC101，每天 09:00 本地，周一至周日）
       └─ 航班实例 Flight Instance（2026-10-20 01:00Z，状态 SCHEDULED）
            └─ 班表航段 Roster Leg（被某个飞行员抽中，sequence=1）
```

- 航班实例是「可被抽取的库存」；一个实例在同一公司内只能被一个班表/自由飞行占用。
- 班表是「任务包」，不是「排班表」；它锁定一架飞机和若干连续航段。
- `aircraft_type.allow_scheduled=false`（如公务机）默认不进入普通班期/抽班；走 `mission_type=CHARTER` 或自由飞行。

### 2.2 配对（Pairing）约束

**软约束：用户每次抽班自由设定**（默认值只是初始值）：

| 约束 | 默认值 | 可调范围 | 说明 |
|---|---|---|---|
| 航段数 | 3 | 1–8 | 抽班时可指定上限 |
| 总飞行时间（合计） | 480min（8h） | 30–1440min | 整条班表所有航段之和，仅用于候选筛选 |
| 每程最短航时 | 30min | 5–1440min | 单段 block 下限 |
| 每程最长航时 | 480min | 10–1440min | 单段 block 上限；`min > max` 返回 `PARAM_OUT_OF_RANGE` |
| 最小过站 | 45min | 15–240min | 前段落地到后段起飞 |
| 最大过站 | 360min（6h） | 30–1440min | 超过则不适合拼成一组 |
| 班表窗口 | 24h | 1–168h | 首段必须在此窗口内开始 |
| 遵循航线 | 开 | 开/关 | 关掉后不依赖航线+班期，用 navdata 机场库任意组合 |
| 不含军用机场 | 开 | 开/关 | navdata `is_military`（缺列时按名称关键词）标记的机场不进候选；飞机当前所在机场不拦 |
| 考虑跑道宽度（翼展） | 开 | 开/关 | 按跑道宽度推翼展上限（<45 m → 36、45–60 m → 52、≥60 m → 80）；45–60 m 是 4D/4E 冲突区，保守按 52 m；无宽度数据不限制 |
| 排除机场 | 空 | 最多不限 | 出发/到达/中转过站都排除 |

- 校验：`max_turnaround_min >= min_turnaround_min`、`min_leg_block_minutes <= max_leg_block_minutes`。
- 这些参数只影响候选生成，不改变已创建班表；`POST /rosters/{id}/redraw` 可带新参数重抽。
- `max_block_minutes` 只限制候选配对的**总**计划飞行时间；班表开始后不再按它中断，超时也可以继续飞。
- 「不遵循航线」生成的候选标 `virtual`：候选阶段不写库，**确认班表时**才落一次性 `flight_instance`（`mission_type=FREE`，无航线/班期），取消班表时置 `CANCELLED`，不会回到候选池。

**硬约束：不可由用户修改**：

| 约束 | 规则 |
|---|---|
| 飞机位置 | 首段出发 = 飞机当前机场 |
| 航段连续性 | 前段到达 = 后段出发 |
| 机型 | 所有航段与飞机机型匹配（`CUSTOM` 机型在班期上无同名机型时允许「机型替换」：到达跑道 ≥ `min_runway_m`、翼展 ≤ 机场 `max_wingspan_m`、距离 ≤ `range_nm × 0.9`） |
| 飞机状态 | `ACTIVE`，无 `HELD/IN_FLIGHT` 锁 |

### 2.3 时间语义（关键）

- 航班实例有**计划时刻** `scheduled_dep_utc / scheduled_arr_utc`，用于需求计算、准点统计、班表展示。
- 玩家不必按真实时钟准点起飞。班表一旦 `IN_PROGRESS`，每个航段可在「上一段落地 + 用户设置的最小过站」之后、班表失效前任意时刻开始。
- 若实际起飞偏离计划超过 **±3h**，标记 `OFF_SCHEDULE`：需求按实际时刻重算，收入额外 -3%，并影响准点率。
- 班表窗口按用户设置（默认 **24h**）：从创建时刻起算，首段必须在此窗口内开始；**首段开始后不再受窗口或总任务时间限制**，直到飞完或被取消。
- 所有存储用 UTC；界面按机场本地时区显示，跨时区自动换算。

### 2.4 抽班流程

```
1. 玩家选择：机型（可空）、基地（可空）、窗口、最大航段数、总飞行时间、每程航时区间、最小/最大过站、是否遵循航线、不含军用机场、考虑跑道宽度（翼展）、排除机场（软约束均可改）
2. 服务端取候选飞机：ACTIVE、无锁、当前位置在基地或任意（若未指定基地）
3. 从飞机当前位置出发，取窗口内的航班实例（`follow_routes=false` 时改为枚举 navdata 机场对），按 2.2 约束拼链；机场池丢掉军用机场、翼展超限的机场
4. 对每个完整配对评分，按「同机最多 1 条、航线形状互不相同」取 Top N（默认 3）；无候选时返回按原因分类的 `reason`
5. 玩家确认一个 → 事务内重新校验 → 创建 roster + 锁飞机（虚拟航段此时才落实例，**随机 3 位航班号**：同 roster 内不复用、`(航班号, 起飞时刻)` 不冲突，极端撞号才退回顺序号）
6. 其他玩家立即看不到这架飞机与这些航班实例
```

### 2.5 评分

```
score = 0.30 * utilization
      + 0.25 * novelty          # prefer_new_airports=false 时 0.15、profit_norm 提到 0.25
      + 0.15 * profit_norm
      + 0.10 * balance
      + 0.15 * leg_credit
      + 0.05 * random
      - loss_penalty

utilization = clamp(total_block_minutes / max_block_minutes, 0, 1)   # 默认 480
novelty     = clamp(新机场绝对数 / 3, 0, 1)        # 单段最多 2 个新机场，不再「新机场/段数」白拿满分
profit_norm = clamp(max(0, estimated_profit) / 50000, 0, 1)
loss_penalty= 0（盈利）或 clamp(|loss| / 200000, 0, 0.35)   # 亏钱长航线不再靠利用率排第一
balance     = 单段 0.6；多段 1 - stddev(每段 block_minutes) / mean(每段 block_minutes)
leg_credit  = clamp(航段数 / max_legs, 0, 1)
random      = uniform(0, 1)
```

- 玩家可在抽班面板看到 `reasons`（机型匹配、含 2 个新机场、过站 55min、预计利润 $18,400、翼展上限 52 m）。
- `prefer_new_airports` 打开时 `novelty` 0.25；关掉时 0.15，`profit_norm` 0.25。
- top3 去重：同一架飞机最多 1 条、航线形状互不相同；虚拟航段的首段起飞时刻按飞机随机错开 0–120 min。

### 2.6 锁定、重抽、取消、过期

| 操作 | 时机 | 规则 |
|---|---|---|
| 锁定 | 确认班表 | 飞机 `ACTIVE → HELD`；创建 `aircraft_lock(lock_type=ROSTER)`，有效期 = 班表窗口 |
| 重抽 | 首段开始前 | **唯一条件：首段未开始（`status=LOCKED`）**；无冷却、无次数上限、无重抽费；旧班表 `CANCELLED`，飞机立即释放 |
| 取消（首段前） | 首段开始前 | 飞行员本人/ADMIN/DISPATCHER 均可；飞行员主动取消记 `no_show_count`，管理/签派取消不计；释放飞机 |
| 过期 | 窗口结束仍未开始（仅 `LOCKED`） | `EXPIRED`，释放飞机，`no_show_count += 1`，收取失约费 |
| 开始 | 首段开始 | `LOCKED → IN_PROGRESS`；飞机 `HELD → IN_FLIGHT`；锁转 `IN_FLIGHT` |
| 取消（首段后） | 首段开始后 | 飞行员本人/ADMIN/DISPATCHER 均可；剩余航段 `CANCELLED`；飞机留在当前位置；飞行员主动取消收 $5,000，管理/签派取消不收；已飞航段正常结算 |
| 完成 | 末段落地并结算 | `IN_PROGRESS → COMPLETED`；飞机 `IN_FLIGHT → ACTIVE`，位置更新为末段到达 |

- **开始后不设总任务时限**：只要还有未完成航段，班表保持 `IN_PROGRESS`，不会因超时自动过期；只能飞完或被取消。
- 重抽、取消、过期都写审计日志；客户端只显示「是否可重抽」，不显示次数/冷却/费用。
- 重抽本身不产生费用；只释放未开始的航段，旧班表 `CANCELLED`。
- 重抽不计失约、不影响抽班优先级；只有飞行员主动取消（首段前）/过期才记 `no_show_count`。
- `roster.redraw_count` 仅用于统计，不参与限制。

### 2.7 自由飞行

- 出发机场只能选「当前有可用飞机」的机场：下拉取自机队去重后的当前位置，不提供空机场；选定机场后再筛该机场的可用飞机。
- 可选任意 `ACTIVE` 且未被锁的飞机；必须从飞机当前机场起飞。
- 可绑定一个 `SCHEDULED` 航班实例（占用该实例），也可自定 `dep/arr/时间`。
- **计划起飞时间**：表单必给字段，留空时默认「当前时间 + 50min」；写入 `free_flight.dep_time_utc`（UTC 落库、本地显示）。
- 自定航线约束：`distance_nm <= aircraft.range_nm * 0.9`；机型满足跑道长度；起降机场在 navdata 中。
- 确认后创建 `aircraft_lock(lock_type=FREE)`，默认 30min；客户端每 60s 心跳；未开始自动释放。
- 开始飞行后锁转 `IN_FLIGHT`；落地结算后飞机位置更新。
- 自由飞行与班表互斥：飞机被班表锁定时不能自由飞；自由飞锁定期间不能被抽中。

### 2.8 并发与冲突

- 确认班表/自由飞都在数据库事务内完成，使用 `SELECT ... FOR UPDATE` 或条件更新。
- `aircraft_lock` 部分唯一索引：`UNIQUE (aircraft_id) WHERE status IN ('HELD','IN_FLIGHT')`；冲突返回 `409 AIRCRAFT_LOCKED`。
- `roster_leg.flight_instance_id` 部分唯一索引：`UNIQUE (flight_instance_id) WHERE status IN ('PLANNED','IN_PROGRESS')`；避免两个班表占用同一航班。
- 客户端断线超过锁 TTL：服务端释放锁，航班 `ABANDONED`，飞机回到 `ACTIVE`（位置取最后已知机场或出发机场，见 §9）。

## 3. 配载生成

### 3.1 生成时机

- 航班 `start` 时由服务端生成，写入 `load_sheet`，并随 `flight_session` 下发给客户端。
- 种子：`seed = HMAC-SHA256(server_secret, flight_record_id)`，客户端不可预测、不可篡改。
- 结算时用同一 seed 重算，与客户端上传的配载比对；不一致以服务端为准并标记 `SUSPECT`。

### 3.2 需求模型

```
base_demand = airport_demand(dep) * airport_demand(arr) / 120
airport_demand: 大型 180 / 中型 90 / 小型 40（按机场 size_class）

route_factor = clamp(1.20 - distance_nm / 5000, 0.35, 1.10)
time_factor  = 早高峰(06-09) 1.10 | 日间(09-17) 1.00 | 晚高峰(17-21) 1.15 | 夜间 0.60
dow_factor   = 周一 1.00 | 周二 0.95 | 周三 0.95 | 周四 1.00 | 周五 1.10 | 周六 0.95 | 周日 1.05
season_factor= 1.00 ± 0.10（按月，可配置）
noise        = uniform(0.85, 1.15)

demand = base_demand * route_factor * time_factor * dow_factor * season_factor * noise
pax_total = round(min(demand, capacity * 0.95))
```

- 若 `demand > capacity * 0.95`，视为溢出（spill），不额外收入。
- 以上仅适用于 `demand_profile=MASS`；`BIZJET`/`VIP`/`CARGO` 见 §3.5，不能套用 95% 客座率。
- 舱位拆分：商务舱比例按机场等级 10% / 6% / 3%，头等舱 0–2%（仅大型机场且机型有头等）。
- 货物：`cargo_kg = min(cargo_capacity, demand * 8 * noise2)`；邮件 = 货物 5%。
- 同一航线当天被重复飞：第 n 次需求乘 `0.92^(n-1)`，最低 0.5（防刷，见 §8）。

### 3.3 重量与燃油

```
oew = aircraft_type.oew_kg
pax_weight = pax_total * 95 kg          # 含行李
cargo_weight = cargo_kg + mail_kg
zfw = oew + pax_weight + cargo_weight

trip_fuel = fuel_burn_kg_h * block_minutes / 60
reserve   = fuel_burn_kg_h * 0.5        # 30min 备份
taxi      = 200 kg
fuel      = min(fuel_capacity, trip_fuel + reserve + taxi + alternate_fuel)
tow       = zfw + fuel

若 tow > mtow：按 货物 → 邮件 → 旅客 → 燃油 的顺序削减，直到 tow <= mtow
若 zfw > mzfw：先减货物，再减旅客
```

- `block_minutes` 优先用航线计划值；无计划值时按 `distance / cruise_speed * 60 + 25min` 估算。
- 备降油量：若选择备降场，`alternate_fuel = fuel_burn_kg_h * (distance_to_alternate / cruise_speed)`。
- 配载单展示：旅客（经济/商务/头等）、货物、邮件、ZFW、TOW、燃油、剩余业载。
- **推出前校验**：实际 ZFW = SimLink `TOTAL WEIGHT − FUEL TOTAL QUANTITY WEIGHT`（两者均为磅，×0.45359237 转 kg）低于配载单 `zfw_kg` 时提示机组「可能漏装旅客/货物」；不阻断推出，差异记录到飞行记录供事后核对。没有 `ZERO FUEL WEIGHT` 这个 SimVar；`FUEL TOTAL QUANTITY` 是体积，不能替代燃油重量。

### 3.4 配载示例

A320（180 座，OEW 42,600kg，MTOW 78,000kg，最大货 9,000kg），ZBAA→ZSSS 612NM，计划 block 130min：

```
base_demand = 180 * 180 / 120 = 270
route_factor = 1.20 - 612/5000 = 1.078
time_factor = 1.00（日间）
dow_factor = 1.00（周四）
demand ≈ 270 * 1.078 * 1.00 * 1.00 * 1.00 = 291
pax_total = min(291, 180*0.95=171) = 171
商务 10% = 17，经济 154
cargo = min(9000, 291*8) = 2328kg；mail = 116kg
zfw = 42600 + 171*95 + 2444 = 61,289kg
trip_fuel = 2400kg/h * 130/60 = 5,200kg；reserve 1,200；taxi 200 → fuel 6,600kg
tow = 67,889kg < 78,000kg（可再加油/加货，按规则以计划油为准）
```

### 3.5 机型角色与特殊构型

`aircraft_type.role` / `demand_profile` 决定配载与收益分支，不能把公务机硬套成 300 座干线客机：

| role | demand_profile | 旅客 | 收入 |
|---|---|---|---|
| `AIRLINER` | `MASS` | 按 §3.2 需求模型 | 票价 × 客座 |
| `BIZJET` | `BIZJET` | 按 `cabin_config_json`，低密度；不套用干线需求 | 整机包机费 = `charter_rate_per_hour × block_hours × market_factor` |
| `VIP` | `NONE` | 预置/0 | 无商业收入，成本照付 |
| `CARGO` | `CARGO` | 0 | 货邮收入 |
| `COMBI` | `MASS/CARGO` | 客+货混合 | 客票 + 货邮 |

**BIZJET 规则**

- `pax_total = min(pax_capacity, max(4, round(pax_capacity × uniform(0.35, 0.80))))`；有包机合同时用合同人数。
- 舱位按 `cabin_config_json` 拆分；`economy=0` 时不出经济舱。
- 收入按整机包机费计算，不按经济舱票价；`charter_rate_per_hour` 由机型配置。
- `market_factor = uniform(0.9, 1.1)`；有包机合同时直接用合同价。
- `allow_scheduled=false`（默认）：不进入普通班期/抽班，只走 `mission_type=CHARTER` 或自由飞行。
- 若管理员强制 `allow_scheduled=true`：按商务/头等票价 × `fare_multiplier`，并提示「非标准运行，可能亏损」。
- 货物默认 0；可配置少量行李。
- `CARGO` 用独立货机需求模型（P1 校准）；MVP 先保证不套用客机 `pax_total` 公式。
- `VIP` 只用于公司/业主任务，收入 0，成本照付；不进入普通抽班。

**A340-300 公务机示例**

- 构型：`first=12`、`business=24`、`economy=0`，`pax_capacity=36`。
- `role=BIZJET`、`demand_profile=BIZJET`、`allow_scheduled=false`、`allow_charter=true`。
- 2h 包机、`charter_rate_per_hour=12,000 USD`：收入约 24,000 USD；成本按 §5 全额计算（燃油/机组/维护/租赁等）。
- 12–28 名旅客是正常现象，不再用 95% 客座率判断「载客太少」。

## 4. 收入

### 4.1 票价

```
fare_economy  = (25 + 0.10 * distance_nm) * airport_tier_multiplier
fare_business = fare_economy * 2.6
fare_first    = fare_economy * 4.0
airport_tier_multiplier: 大型 1.10 / 中型 1.00 / 小型 0.90
# 起降机场等级不同时，取两场的平均值
```

### 4.2 收入项

```
pax_revenue   = pax_economy*fare_economy + pax_business*fare_business + pax_first*fare_first
cargo_revenue = cargo_kg * 0.45
mail_revenue  = mail_kg * 0.30
ancillary     = pax_total * 6.00
revenue       = pax_revenue + cargo_revenue + mail_revenue + ancillary
```

### 4.3 准点与偏离

| 情况 | 调整 |
|---|---|
| 实际起飞在计划 ±15min | `revenue *= 1.02` |
| 偏离 15–60min | 无调整 |
| 偏离 > 60min | `revenue *= 0.95` |
| 偏离 > 3h | `revenue *= 0.97` 且按实际时刻重算需求（已含 `OFF_SCHEDULE`） |
| 备降 | 收入按实际到达机场重算，且 `revenue *= 0.50` |
| 取消/中止 | 无收入（已登机旅客按 20% 收取，可选） |

## 5. 成本

```
fuel_cost        = fuel_used_kg * fuel_price                  # 默认 1.05 USD/kg，可按机场覆盖
landing_cost     = mtow_ton * 24.00 + night_surcharge(50)     # 夜间 22:00-06:00 本地
handling_cost    = pax_total * 11.00 + cargo_ton * 30.00
crew_cost        = block_hours * 900.00
maintenance_cost = block_hours * 600.00 + cycles * 60.00
lease_cost       = block_hours * lease_per_hour               # 租赁机；自有机用折旧率
parking_cost     = parking_hours * 20.00                      # 到达后停机，前 2h 免
atc_cost         = distance_nm * 0.70
insurance_cost   = revenue * 0.012
total_cost       = fuel + landing + handling + crew + maintenance + lease + parking + atc + insurance
profit           = revenue - total_cost
```

- `fuel_used_kg` 优先用遥测的首尾油量差；缺失时用计划油耗。
- 自有飞机：`lease_cost = block_hours * depreciation_per_hour`（默认按机型价的 0.02%/h）。
- 过站时间超过 2h 的部分按停车费计。
- 备降：额外航段成本 + 备降场 landing/handling + 机组加班；收入按 §4.3 减半。
- 取消：收取计划成本的 20%（地面服务、机组、停机）。
- 坠机：`repair_cost = hull_value * 0.10`；飞机 `MAINTENANCE` 48h；无收入；保险赔付 `hull_value * 0.30`（可选，默认开）。

### 5.1 成本示例（接 §3.4）

```
fuel 5,210kg * 1.05 = 5,470.5
landing 78t * 24 = 1,872
handling 171*11 + 2.328t*30 = 1,881 + 69.8 = 1,950.8
crew 130/60 * 900 = 1,950
maintenance 130/60 * 600 + 1*60 = 1,360
lease 130/60 * 2,000 = 4,333.3
parking 2h = 0（前 2h 免）
atc 612.4 * 0.70 = 428.7
insurance ≈ 0.012 * revenue
```

## 6. 结算与账本

### 6.1 结算流程

```
flight_record.validation_status = VALID/SUSPECT
  → 读取 flight_record 实际数据 + load_sheet + economy_snapshot（含 settlement_policy）
  → 重算收入/成本（服务端权威）
  → 写 settlement（revenue_total/cost_total/profit/breakdown_json）
  → 写 ledger_entry（逐项，事务）
  → 更新 company.balance（缓存列，和账本同事务）
  → 更新 aircraft（位置、总小时、循环、油量、状态）
  → 更新 flight_instance/roster_leg 状态
  → 写同步事件 flight.completed / company.balance（客户端下次 GET /sync 获取）
```

### 7.1 机型参数口径（自定义机型模板）

`aircraft_type` 是唯一真值来源：配载（`generate_load_sheet`）、航时估算（`estimate_block_minutes`）、推荐（跑道/航程过滤）、异常策略的机型覆盖与结算成本都读它。内置模板由 `specs.py` 的 `CATEGORY_DEFAULTS` + `SPEC_OVERRIDES` + `data/aircraft_types.json` 生成（`source=BUILTIN`，只读）；玩家可在「机队 → 机型模板」新增 `CUSTOM` 机型并随时改参数。

| 字段 | 校验 |
|---|---|
| `oew_kg` / `mzfw_kg` / `mlw_kg` / `mtow_kg` | `0 < OEW < MZFW ≤ MTOW`、`MLW ≤ MTOW`（必填） |
| `pax_capacity` + `cabin_config_json` | 座位数 = 客舱构型（first/business/premium_economy/economy）合计 |
| `fuel_burn_kg_h` | 0.1–30,000（> 0） |
| `cruise_speed_kt` | 60–600 |
| `min_runway_m` | 0–5,000 |
| `wingspan_m` | 0–90；0/留空 = 按 `min_runway_m` 推保守值（<1800 → 36 / <2500 → 52 / <3200 → 60.3 / 其余 65 m） |
| `range_nm` | 1–20,000 |
| `fuel_capacity_kg` / `cargo_capacity_kg` | ≥ 0（缺省按 MTOW − OEW） |
| `lease_per_hour` / `charter_rate_per_hour` / `fare_multiplier` | ≥ 0 / ≥ 0 / 0.2–10 |

- 越界返回 `PARAM_OUT_OF_RANGE`，`details.key` 指明字段，前端表单就地高亮；`BUILTIN` 机型 `PATCH`/`DELETE` 返回 `BUILTIN_TYPE_READONLY`，只能「复制为自定义」。
- 录制建档的机型优先级：任务上下文 → SimLink `aircraft_title` 匹配（自定义 `title_keyword` 优先，内置机型按 `specs.TITLE_KEYWORDS` + ICAO）→ 设置里的「默认机型」；「默认机型」只用于航路规划/推荐，收尾与统计都读建档时已存的机型。
- 删除仅限 `CUSTOM`，仍被机队/班期/未完成航班实例引用时返回 `AIRCRAFT_TYPE_IN_USE`。
- 结算的 `COST_FUEL = 实际燃油 × fuel_price`（`fuel_price` 来自航班开始时的经济快照）；改机型油耗只影响之后的航班。

## 8. 防作弊与平衡

### 8.1 权威来源（M2 本地 / M3 服务端）

- 客户端只提交轨迹与摘要，**不提交金额**；金额由 `aoc-core`（M2）或服务端（M3）计算。
- 配载 seed 由权威侧生成并保存在 `load_sheet`；客户端无法预知或重放（M2 用本地 secret，仅防误用，不作为对抗）。
- `session_token` 短有效期（默认 6h），与 `flight_record` 绑定；换机/重放无效。
- 遥测批次签名；权威侧校验 seq、时间、坐标、速度、油量（M2 本地校验只做提示与标记）。
- 摘要与轨迹不一致时，以轨迹重算为准。

### 8.2 常见刷钱路径与对策

| 路径 | 对策 |
|---|---|
| 短途往返刷载客率 | 同航线当日重复需求衰减；最低 block time 计入成本；起降费/滑行成本固定 |
| 时间加速 | 按 `settlement_policy` 分档折算；默认 >8x `REJECT` |
| 反复重抽找高收益班 | 重抽无冷却/次数/费用；候选收益带随机噪声；未飞不结算，重抽本身不产生收益 |
| 改客户端配载 | 服务端 seed 重算；不一致标记 |
| 伪造轨迹 | 包线校验、距离/时间比、瞬移检测、起降一致 |
| 断线逃结算 | 未 finish 不结算；航班 `ABANDONED`；飞机回收 |
| 多开账号刷同一飞机 | 飞机锁 + 公司内唯一航班实例 + 设备/账号审计（P1） |
| 坠机骗保险 | 保险赔付 < 修理费；频繁事故提高保费（P2） |

### 8.3 平衡目标

- 单班净利润率中位数 **5%–15%**；短途高频率、长途高票价但成本也高。
- 一架窄体机每天 6–10 班，公司 30 天内存活率 > 80%（单人中等难度）。
- 不让「最优解」唯一：新机场奖励、时刻、机型、载客率都有取舍。
- 上线前用 1,000 班合成数据跑分布；参数改动后回归。

## 11. 异常与结算策略

### 11.1 检测与处置分离

`02-系统架构.md` §7.5 只负责**检测**异常（数据缺口、时间加速、暂停、瞬移、油量跳变等），产出 `anomaly` 事件；**怎么处理**由公司配置决定。

这样同一套检测可以服务不同风格的公司：

- 硬核公司：数据缺口直接拒绝；
- 休闲公司：接受，只记录；
- 中等：按缺口/加速比例折算；
- 争议场景：进入人工复核。

### 11.2 动作

| 动作 | 结算结果 | 典型场景 |
|---|---|---|
| `ACCEPT` | 正常结算；`validation_status=SUSPECT`，记录警告 | 小缺口、休闲服 |
| `REJECT` | 收入 = 0，`payout_factor=0`；成本按 `reject_cost_mode`（`FULL` / `DIRECT_ONLY` / `NONE`） | 瞬移、严重加速、伪造 |
| `WEIGHTED` | 按公式折算收入；成本照扣 | 数据缺口、暂停、轻度加速 |
| `REVIEW` | 结算挂起 `HELD`，进入复核队列；复核人可改判为 `ACCEPT`/`WEIGHTED`/`REJECT`（M2 本人 / M3 管理员） | 证据不足、争议 |

- 多个异常同时触发时，按严重度取最高：`REJECT > REVIEW > WEIGHTED > ACCEPT`。
- `REJECT` 不是删除航班：航班、轨迹、审计保留；飞机位置按实际落地更新。
- `REJECT` 默认仍生成 `settlement`（`status=SETTLED`、`payout_factor=0`、`policy_action=REJECT`），以便记录成本；`reject_cost_mode=NONE` 时 `status=VOID`。
- `REVIEW` 可按 `review_advance_ratio` 预付（0–0.5，默认 0）；最终结算多退少补。

### 11.3 默认规则

| 异常 | 默认动作 | 阈值 / 公式 | 说明 |
|---|---|---|---|
| 数据缺口 | `WEIGHTED` | 每 10min -5%，最多 -30%，全局最低 factor 0.4 | 相邻点时间差 > 5min |
| 时间加速 2–4x | `WEIGHTED` | -20% | 加速点占比 > 5% |
| 时间加速 4–8x | `WEIGHTED` | -50% | 同上 |
| 时间加速 > 8x | `REJECT` | — | 视为作弊 |
| 暂停占比 > 20% | `WEIGHTED` | -10% | 暂停时长 / block time |
| 瞬移 | `REJECT` | — | 相邻点速度 > 900kt 持续 2 点 |
| 油量跳变 | `REVIEW` | — | 单点变化 > 总油量 20% |
| 轨迹距离异常 | `REVIEW` | 轨迹 / 大圆 < 0.9 或 > 2.5 | |
| 轨迹缺失 / 校验和不符 | `REVIEW` | — | 无法复核时可改判 `REJECT` |
| 其他未列异常 | `REVIEW` | — | 默认保守 |

- 起降不符、备降、坠机、落错机场属于**运行事件**，走 §9 固定规则，不进入本策略表。
- 默认 `reject_cost_mode = FULL`：收入为 0 时，燃油/起降/地面服务/机组/维护/租赁等实际成本仍扣，防止「断开逃费」；管理员可改为 `DIRECT_ONLY` 或 `NONE`。
- 默认 `review.sla_hours = 24`；超时未复核可按保守的 `WEIGHTED` 结算（可配置为继续挂起）。

### 11.4 折算公式

```
payout_factor = 1.0
review_required = false

for anomaly in triggered:
    if action == REJECT:
        payout_factor = 0
        break
    if action == REVIEW:
        review_required = true
        continue
    if action == WEIGHTED:
        penalty = min(max_penalty, base_penalty + per_unit * units)
        payout_factor -= penalty

payout_factor = clamp(payout_factor, min_payout_factor, 1.0)

revenue_settled = revenue_gross * payout_factor
cost_settled = cost_gross                 # 默认全额
profit = revenue_settled - cost_settled
```

- `units` 由异常定义：数据缺口 = 分钟 / 10；暂停 = 占比 / 10%；加速 = 按档位固定扣减。
- 全局 `min_payout_factor` 默认 0.4，避免数据缺口把长途航班扣成 0。
- `REVIEW` 期间不写 ledger；复核后按最终动作写。
- `REJECT` 且 `reject_cost_mode = NONE`：成本也不扣，等于整班不结算（`settlement=VOID`）；仅建议测试/休闲服使用。

### 11.5 示例

ZBAA→ZSSS，毛收入 20,910，总成本 17,606：

| 情景 | 计算 | 净利润 |
|---|---|---|
| 数据缺口 12min | factor = 1 - 12/10×5% = 0.94 | 20,910×0.94 - 17,606 = **2,049** |
| 时间加速 3x | factor = 1 - 20% = 0.80 | 20,910×0.80 - 17,606 = **-878** |
| 瞬移（REJECT，FULL） | 收入 0，成本照扣 | **-17,606** |
| 数据缺口 12min 且政策为 REVIEW | 挂起，不写账本 | 待复核 |

### 11.6 复核流程

```
flight.finish
  → 检测 anomaly，读取 settlement_policy + 航班快照
  → 计算最高优先级动作
  → ACCEPT / WEIGHTED：写 settlement + ledger
  → REJECT：revenue=0；按 reject_cost_mode 写成本；settlement 完成
  → REVIEW：settlement 状态 HELD；写复核队列；不写 ledger
  → 复核人处理（M2 客户端复核队列 / M3 /admin/ops/review）：ACCEPT / WEIGHTED / REJECT + 备注
  → 写 ledger、更新 settlement、审计
```

- 复核页展示：异常列表、轨迹、落地指标、配载、预估金额、政策建议。
- `HELD` 期间航班实例保持 `LANDED`；复核完成后按结果推进到 `SETTLED` 或保持无效。
- 管理员可手动覆盖 `payout_factor`（0–1），必须填原因。
- 复核结果通知飞行员；争议可再次提交（P1）。

### 11.7 REJECT 成本模式 `reject_cost_mode`

| 值 | 扣哪些成本 | settlement 结果 |
|---|---|---|
| `FULL`（默认） | 燃油、起降、地面、机组、维护、租赁、停车、空管、保险 | `SETTLED`，收入 0 |
| `DIRECT_ONLY` | 燃油、起降、地面、空管 | `SETTLED`，收入 0 |
| `NONE` | 不扣 | `VOID` |

- 成本项按 §5；`DIRECT_ONLY` 不含机组/维护/租赁/保险。
- 若此前已预付，`NONE` 仍需写 `ADVANCE_CLAWBACK`，结算状态可保持 `VOID`。
- 管理员可在网页端切换；只影响后续航班。

### 11.8 REVIEW 预付款 `review_advance_ratio`

- 范围 0–0.5，默认 0（不预付）；0.5 为上限，防止超额预付。
- `advance_amount = max(0, estimated_profit) * review_advance_ratio`；`estimated_profit` 用航班开始时的配载与预估成本。
- `HELD` 时写 `ADVANCE_PAYOUT`；最终结算：

```
final_profit = revenue_settled - cost_settled
adjustment = final_profit - advance_amount
```

- `adjustment > 0` 写 `REVENUE_ADJUSTMENT`；`adjustment < 0` 写 `ADVANCE_CLAWBACK`（净回冲，可能包含成本；允许公司余额为负）。
- 若最终 `REJECT`，全额 clawback（可能同时扣成本）。
- `settlement.advance_amount` 存预付款；`policy_breakdown_json` 记录调整。

### 11.9 作用范围 `scope_mode`

| 值 | 行为 |
|---|---|
| `COMPANY_ONLY`（默认） | 只用公司默认策略；忽略机型/单机/飞行员覆盖 |
| `ALLOW_OVERRIDES` | 允许覆盖；按优先级合并 |

- `scope_mode` 只允许公司级设置，不能出现在 overrides 中。
- 覆盖类型：`AIRCRAFT_TYPE`（机型）、`AIRCRAFT`（单机）、`PILOT`（飞行员）。
- 合并顺序：公司默认 → 机型 → 单机 → 飞行员；**越具体优先级越高**。
- 覆盖只写要改的字段（深合并），未写字段继承上一层。
- 例：公司数据缺口 `WEIGHTED`；A320 机型覆盖为 `REJECT`；某飞行员覆盖为 `REVIEW` → 该飞行员飞 A320 时用 `REVIEW`，飞其他机型用公司默认。
- 覆盖配置存在 `settlement_policy.overrides` 数组，随同一配置版本发布/回滚/审计。
- 注意：当前是「越具体越优先」，飞行员覆盖可以放宽机型限制；若不允许放宽，用 `COMPANY_ONLY`，或后续增加「最严格优先」模式。
- 航班开始时把**合并后的有效策略**写入 `economy_snapshot`；结算只读该快照。
- 网页端提供「生效预览」：选飞行员 + 飞机，显示最终规则及来源（公司/机型/单机/飞行员）。

### 11.10 配置与权限

- 配置键：`company_setting.settlement_policy`，与经济参数一样走 `company_config_version` + `company_setting_history` + 审计。
- 网页管理端页面：`/admin/policies/settlement`；运行复核：`/admin/ops/review`。
- 权限：`ADMIN` 改策略（含覆盖）；`DISPATCHER`（P1）可复核但不能改策略；`PILOT` 不可访问。
- 支持「预览」：选择异常组合，实时显示 `payout_factor`、收入、成本、利润；选择飞行员 + 飞机可看合并后的有效策略。
- 修改策略只影响之后的航班；已开始/已结算航班用各自的快照。
