## 0. 一句话结论

需求可做，**数据也有**（Little Navmap 的 `parking` 表里就是停机位，此前一直没人读）。但「到达前 30 分钟推送」这句话里有四个需要定的口径：

1. **机位从哪来** → 场景库 `little_navmap_msfs24.sqlite` 的 `parking` 表（本机实测 30.2 万个机位 / 2.27 万座机场），现实 navdata 的 `parking` 只有编号没有尺寸（2093 座机场）；
2. **什么时候算「前 30 分钟」** → 已定（Q-1）：`ETA ≤30 min` 与 `距到达 ≤150 NM` **两者先到**触发，进近阶段兜底；阈值可调；
3. **「发送」走哪条通道** → **不能挂在前端定时器上**：`App.tsx` 的 pulse 轮询在 `document.hidden` 时直接暂停（`apps/client/src/App.tsx:251`），玩家在 MSFS 里全屏飞的时候页面一定是 hidden。触发必须落在 `aoc-core`，投递必须由常驻进程（Tauri 外壳 / 便携启动器）去做。**Hoppie ACARS 确实能把机位直接推到机载 MCDU**（走 `type=telex`，机型支持即可），但有四个硬前提，见 §6.1；已定（Q-2 / Q-6 / Q-10 / Q-11）：**Hoppie telex + 系统通知 + 置顶浮窗，且 ACARS 与客户端双发**；**BeyondATC 在线即让位**（Q-7），它的 ATIS 端点**不做借用**（实测本机不通，Q-11）；本地模式也不能靠 SimConnect 往屏幕上写字（该 API 已废弃，官方标注不能用于 MSFS 2020），只走自己的浮窗（§6.3.2）。

4. **航站楼按航司归属**（虹桥 T1 只给春秋/河北/厦门 + 国际、羽田 T1 只给 JAL）→ 数据里**没有**现成字段（`airline_codes` 全表 0 填充、`apron` 表 0 行、`name` 在虹桥全是 `P`），但机位坐标成簇，可用「命名机位集合 + 承运人规则」两层表精确重建，见 §4.5。已定：规则由**个人设置 + 联机管理端**维护（Q-8），未命中时**排他已声明的航站楼**（Q-9），界面**只显示编号**、不拼航站楼标签（Q-4）。
5. **单机模式怎么投递（已定 D-1 / D-2）** → 能进机舱就进机舱，做不到就用 AOC 浮窗 + 系统通知，并**在界面上写明为什么没走机内**（原因码见 §6.4）。2026-11-06 实测：BATC 那条在本机不通（没装 BATC 时 Fenix 不发请求，取证见 §6.3.1）；**Hoppie 那条通了 —— iniBuilds A350 的 Mailbox 收到，端到端约 30 s**（V-14）。所以单机顺序 = **Hoppie（有 logon 且机型支持）→ 浮窗 + 系统通知**，并按 Q-6 双发。

推荐组合（按已拍板口径）：**P0 读机位 + 确定性选位 + 执行页展示** → **P0.5 航站楼/承运人规则** → **P1 触发 + 落库 + 应用内通知** → **P2 系统通知 + 便携托盘气泡 + 置顶浮窗** → **P2.5 Hoppie telex 直投** → **P3 联机分配与冲突避让**。合计粗估 **8.5–12.5 人天**（不含测试走查）。

## 1. 需求澄清

| 问题 | 结论（本文档口径） |
|---|---|
| 「停机位」是什么 | 到达机场的一个具体停机位（gate / stand / ramp），例如 `G340`、`532`。**不是**跑道、不是登机口时间、不是滑行路线 |
| 「发送」是什么 | 一条**到达前提醒**：机场 + 预计到达时刻 + 预计停机位 +（有的话）廊桥/区域 + 数据来源 |
| 单机 vs 联机 | 单机/个人模式没有「别人在抢机位」，本质是**确定性选位**；联机模式才需要真正的**分配 + 冲突避让 + 签派改派** |
| 是否影响结算 | 本期不影响。停机费 `COST_PARKING` 只在账本类型白名单里（`packages/aoc_core/aoc_core/ops/service.py:69-78`），默认参数 `parking_per_hour=20`/`parking_free_hours=2`（`ops/specs.py:199-200`）无人消费，`economy.py` 的 8 项成本里也没有它 —— 04 §7 的公式尚未落地。机位可以作为将来停机费的输入，但不在本需求范围 |
| 是否会把飞机放进机位 | **不会**。与 §35 快速调机同性质：只在 AOC 侧给信息，模拟器里飞机停在哪由玩家决定。文案必须写清，否则会被当成「功能没生效」 |

**不做什么**（避免范围失控）：

- 不做滑行引导 / 机坪路由（taxi routing）、不做廊桥动画与地面服务模拟；
- 不写回模拟器（不修改飞机位置）；
- 不做真实世界航班动态（FlightAware）驱动的机位；
- 不做「机位预订/抢占」时间表 UI（联机 P3 只做算法内的占用，不做玩家可编辑的机位牌）。

## 3. 方案 A：机位数据从哪来

| 编号 | 方案 | 优点 | 缺点 | 取舍 |
|---|---|---|---|---|
| S1 | 场景库 `parking`（`little_navmap_msfs24.sqlite`） | 有编号/尺寸/廊桥/朝向；与模拟器一致；零新增配置（同一路径已被 §36 使用） | 覆盖率取决于玩家是否用 LNM 扫过场景；add-on 机场可能没扫 | **主源（推荐）** |
| S2 | 现实 navdata `parking` | 无需扫描；全球编号 | 只有编号，无尺寸/廊桥；覆盖率 12% | **回退源**（只显示编号，标注「无尺寸数据」） |
| S3 | 手工覆盖表 `airport_stand_override` | add-on 机场/自制机场可救；与 §43 跑道覆盖同一模式 | 要用户手动填 | **做（表 + API），UI 可与跑道覆盖共用一张卡片** |
| S4 | 历史学习：AOC 自己记录的「到机位」最后位置 | 零外部依赖；可校验 S1 的编号（最近机位 ≤80 m）；可在无 `parking` 表的机场生成候选 | 冷启动为 0；坐标是像素级近似 | **做（写 `stand_sample`，用于校验 + 打补丁）** |
| S5 | SimConnect Facility API 实时查机位 | 最真 | V-3 已证字段名需官方 CSV，当前拿不到 | **不做** |

**优先级**（与 `runways()` 完全同构，便于复用同一套「来源」语义）：

```
airport_stand_override（source=override）
  → 场景库 parking（source=scenery）
    → 现实 navdata parking（source=navdata，仅编号）
      → 无数据（source=none，明确提示「无停机位数据」，不编造）
```

**实现要点**：`NavData` 已有 `self._scenery`（`navdata.py:188-195`），新增 `stands(icao)` 只需仿 `runways()`（`navdata.py:538-555`）按机场懒加载 + 缓存（`self._stands: dict[str, list[dict]]`），并且用 `pragma table_info(parking)` 探测列名（老库/异种库可能缺 `has_jetway`/`suffix`），缺列降级而不是报错 —— 这是 `_columns()`（`navdata.py:198-202`）现成的写法。

## 4. 方案 B：怎么「选」机位

单机模式没有并发，本质是**确定性选择**而不是分配；但评分函数必须和联机的分配共用，否则两套口径。

### 4.1 硬约束（不满足直接排除）

1. **尺寸**：`radius >= wingspan_m`（翼展来自 `aircraft_type.wingspan_m`，§26/§38 已有真值）；`radius` 缺失（现实 navdata）→ 跳过尺寸判断，标记 `size_unknown=true`。**注**：若 V-7 实测发现 `radius` 与翼展不是 1:1（实测 GE 档 121–164，远超 A380 的 79.8 m），则改为按系数折算后再比，系数写成常量而不是散落各处。
2. **用途**：按机型 `role/variant` 分池
   - `AIRLINER` / `COMBI` → `GS/GM/GH/GE`（有则只用带廊桥的池，见 4.2）
   - `CARGO` → `RC/RMC`（不足时退 `GH/RGAL`）
   - `BIZJET` / `VIP` → `RGA*/DGA/GS`
   - 机场 `is_military` 与 `RMC/RMCB` 互斥（`is_military` 已在 `navdata.py:240`）
3. **无效位**：`FUEL`、`UNKN`、`VEHICLE` 一律排除（`FUEL` 占比 6%，最容易误选）。
4. **航站楼归属**：按 §4.5 的规则表过滤（虹桥 T1 只给春秋/河北/厦门 + 国际，羽田 T1 只给 JAL 这类）。规则缺失时不硬拦，规则命中但过滤为空时回退并告警。

### 4.2 打分（越小越优先）

| 维度 | 权重 | 说明 |
|---|---|---|
| 廊桥 | −20（客机）/ +10（货机） | `has_jetway=1` |
| 尺寸贴合 | −(abs(radius − wingspan_m) / 10) | 别把 B738 塞进 A380 位 |
| 靠近落地跑道 | −(距离 NM) | 事前只有「到达机场最长跑道入口」可用（无风数据，见 §5.3） |
| ~~航司代码命中~~ | 删除 | 实测 `parking.airline_codes` 在场景库与现实现实库里**非空行数都是 0**（30.2 万 / 5.8 万行），该维度是死代码 → 改用 §4.5 的规则表做航司归属 |
| 历史一致 | −10 | 该注册号/该航班上次停过的机位（`stand_sample`） |
| 编号稳定哈希 | 0（仅排序） | `sha1(flight_record_id + stand_ident)` 打破同分，保证「同一航班每次算同一个位」 |

输出：`stand_ident = f"{name}{number}{suffix or ''}"`（EGLL → `G340`；`P212R` 原样保留），并回传 `lat/lon/heading/has_jetway/radius/source/score_breakdown`。**Q-4 已定：`stand_ident` 就是界面展示值**，不再追加区域/航站楼标签（LNM 没有航站楼字段，硬拼会误导）。

### 4.3 稳定性与变更

- **定稿**：第一次算出即写库（`flight_stand.status=PROPOSED`），之后同一 `flight_record_id` 不再重算；
- **允许重算的唯一条件**：机位数据「从无到有」（用户这时才配/扫了场景库）→ 重算后 `status=CHANGED`，并允许发第二条「机位变更」通知；
- **不允许**因为 ETA 抖动、地速变化而改机位（否则玩家按 A 位滑行、通知变成 B 位）。

### 4.4 联机（P3）才需要的东西

- 占用键：`(airport_icao, stand_ident, time_window)`，窗口 = `落地 − 20 min` ~ `落地 + 过站时间`；
- 冲突时取次优并写 `ops_audit(STAND_REASSIGN)`；签派可在管理端强制改派；
- 客户端在联机模式下**不得自行改派**（与 IA-07「联机只读」同口径），离线时本地算、回传后以服务端为准。

### 4.5 航站楼与承运人归属（虹桥 T1 只给春秋/河北/厦门 + 国际、羽田 T1 只给 JAL）

**先说结论：数据里没有「航站楼」这个字段，但可以从机位坐标精确重建。**

实测三条路都是死的：

| 可能的数据源 | 实测结果 | 结论 |
|---|---|---|
| `parking.airline_codes` | 场景库 301,732 行 / 现实库 58,323 行，**非空 0 行** | 不能用来判航司 |
| `parking.name`（区域字母） | 虹桥 166 个机位**全是 `P`**；羽田只有 `P`(152) / `G`(74) / `GV`(2) | 只在少数机场有区分度，不能当航站楼 |
| `apron` 表（停机坪多边形） | 两个库都是 **0 行** | 没有面数据可用 |

但机位坐标本身是成簇的。虹桥实测（`number` 按百位分组）：

| 编号段 | 数量 | 平均经度 | 实际方位 |
|---|---|---|---|
| 1xx / 3xx / 5xx | 13 / 42 / 19 | 121.341 | 东侧 → **T1** |
| 2xx / 4xx / 6xx | 67 / 16 / 9 | 121.327 | 西侧 → **T2** |

所以本文档把「航站楼」定义成**一个命名的机位集合**，由 matcher 圈定，四种 matcher 可按「或」叠加：

| matcher | 适用 | 虹桥 | 羽田 |
|---|---|---|---|
| `number_range` | 编号按段分区（最常见） | `100-199, 300-399, 500-599` | `1-506` 按段 |
| `area_prefix` | `parking.name` 有区分度时 | 不适用（全是 `P`） | `G`（74 个，全带廊桥） |
| `radius` | 布局不规则 / 编号乱 | 可选（圆心 + 半径） | 可选 |
| `explicit` | 少量特殊位 | `601-608` | 远机位 |

#### 数据模型：机场事实与承运人规则分两张表

```sql
-- ① 机场事实：T1 是「哪一片机位」（与航司无关，一座机场只维护一次）
CREATE TABLE IF NOT EXISTS airport_terminal (
    icao TEXT NOT NULL, terminal TEXT NOT NULL,     -- terminal: 展示名，如 T1
    matchers_json TEXT NOT NULL,                    -- number_range / area_prefix / radius / explicit
    note TEXT, source TEXT NOT NULL DEFAULT 'USER', -- USER / SAMPLE / ADMIN
    verified_at TEXT, updated_at TEXT NOT NULL,
    PRIMARY KEY (icao, terminal)
);

-- ② 承运人规则：T1 给谁用（可多条，OR 语义）
CREATE TABLE IF NOT EXISTS terminal_rule (
    id TEXT PRIMARY KEY,
    icao TEXT NOT NULL, terminal TEXT NOT NULL,
    scope TEXT NOT NULL DEFAULT 'BOTH',             -- DOMESTIC / INTERNATIONAL / BOTH
    airlines_json TEXT NOT NULL DEFAULT '[]',       -- ['9C','HBH','CXA']；空数组 = 任意航司
    priority INTEGER NOT NULL DEFAULT 0,
    enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);
```

两张表分开的理由：虹桥的 T1 位置是**机场事实**（改一次），「T1 给谁」是**运行规则**（春秋/河北/厦门 + 国际 = 3 条规则），联机时还要允许签派按公司改而不动机场定义。

按这个模型，用户举的两个例子落成数据是这样：

```jsonc
// 虹桥：T1 = 东侧奇数百位
{ "icao": "ZSSS", "terminal": "T1",
  "matchers": [{ "type": "number_range", "ranges": [[100,199],[300,399],[500,599]] }] }
{ "icao": "ZSSS", "terminal": "T1", "scope": "DOMESTIC",
  "airlines": ["9C","HBH","CXA"] }        // 春秋 / 河北 / 厦航
{ "icao": "ZSSS", "terminal": "T1", "scope": "INTERNATIONAL",
  "airlines": [] }                        // 国际，任意承运人

// 羽田：T1 = 一撮坐标，只给 JAL 集团国内
{ "icao": "RJTT", "terminal": "T1",
  "matchers": [{ "type": "radius", "lat": 35.5494, "lon": 139.7797, "r_m": 900 }] }
{ "icao": "RJTT", "terminal": "T1", "scope": "DOMESTIC",
  "airlines": ["JAL","JTA","HAC"] }
```

#### 判定顺序（确定性，先算的赢）

1. **航班国内/国际**：`dep.country != arr.country` → `INTERNATIONAL`，否则 `DOMESTIC`（navdata 已有 `country`/`iso_country`，`navdata.py:221-241`）。这是近似口径：港澳台、申根、美加之间的实际运行按国内处理，**允许规则里按机场/航线覆盖**（`scope` 可显式指定）。
2. **本航班承运人集合**：新增公司级 `airline_codes`（多值，IATA 2 位 / ICAO 3 位 / 呼号前缀，如 `9C,HBH,CXA` = 春秋/河北/厦航）。AOC 默认是虚构航司（D-11），所以也允许把自家前缀（如 `AOC`）写进某个 terminal 的 `airlines`，效果就是「我们固定用 T2」。
3. **命中规则** → 只用该 terminal 圈定的机位。
4. **没有任何规则命中**（例如羽田我们不是 JAL/ANA）→ 用「**未被任何承运人声明的机位**」，而不是「全部机位」。这样虚构航司不会被派到 JAL 专属的 T1，这是这个需求的关键语义。
5. **过滤后为空** → 回退到「忽略航站楼」+ `warnings[]`（同 §34 放宽阶梯：宁可放宽并说明，也不静默给个错位、更不能一个位都给不出来）。
6. 结果落 `flight_stand.terminal` + `terminal_source`（`rule` / `company_pref` / `none`）。**Q-4 已定：界面只显示编号（如 `G340`）+ 一个「按承运人规则」的小标记，不写 `T1`/航站楼字样** —— 航站楼是筛选依据，不是我们敢向玩家承诺的事实。

#### 规则从哪来（维护方式）

- **不随包分发真实世界数据**：航司搬航站楼、机场改扩建都会过时，而且本项目默认虚构航司（D-11），照抄现实规则反而会挡路。提供 `data/terminal_rules_sample.json` 示例包（约 10 座：虹桥、羽田、首都、浦东、希思罗、肯尼迪…），标 `source=SAMPLE`，可一键整体关闭。
- **单机在设置页维护，联机在管理端维护（P3）**（Q-8 已定：两处都要），与跑道覆盖（§43）同一套 CRUD + 审计风格。
- **维护 UI 比字段更重要**：把该机场的机位点画在地图上（复用 `TrackMap`/`WorldMap` 的 MapLibre 底图），**框选/圈选一批点 → 命名 T1**，再勾承运人与国内/国际；手填编号区间作为高级入口（虹桥只需三行）。
- 支持 JSON 导入导出，便于社区互换（与机型模板、档案 zip 同一口径）。
- 维护提示：`verified_at` + 界面标「2026-11 校对」，超过 12 个月提醒复核（这类数据一定会旧）。

#### 与打分的关系

航站楼是**硬过滤**（不满足就不进候选），所以 §4.2 里的「航司代码命中」软加分删掉了（本来也是死代码）。「历史一致」（该航班/该注册号上次停过的位）保留，因为它能在规则未覆盖的小机场起作用。

## 5. 方案 C：什么时候发（「前半小时」到底怎么判）

### 5.1 为什么不能只用「30 分钟」

- 现有 ETA 是 `大圆剩余 ÷ 当前地速`，**下降段地速从 450 kt 掉到 140 kt**，越接近越低估时间；巡航段又因为不走航路里程（大圆比航路短 5–10%）而偏低；
- ETA 在 ±3–8 min 之间抖，玩家一个加速/一次等待航线就会来回穿越 30 min 阈值 → 重复通知或永远不通知。

### 5.2 先修 ETA（三档分段，仍然只用现成数据）

```
剩余 > 60 NM : ete_min = remaining_nm / gs_kt * 60
20–60 NM     : ete_min = (remaining_nm - 20) / gs_kt * 60 + 20 / 250 * 60
< 20 NM      : ete_min = remaining_nm / 180 * 60 + 3        （进近 3 min 含落地）
再乘航路绕行系数 detour = route_distance_nm / great_circle_nm（有航路且值在 1.0–1.3 时才用）
```

输出 `eta_min`（新增 `eta_refined_min`，老字段不动）+ `eta_confidence`（`high` <20 NM / `medium` <60 NM / `low` 其余）。

### 5.3 「落地跑道」目前只能近似

SimLink **没有采集风向风速**（`apps/simlink/Models.cs` 的 `Sample` 无 wind 字段，全仓无 `wind_dir`）。所以「按风选跑道」只能等补遥测。本期绕过：

- 优先用航班航路的 `default_star` 关联跑道（`ops_route.default_star`）；
- 否则用到达机场最长跑道；
- 落地后 `landing.evaluate()` 已能识别实际跑道 → 只用于「实际机位 vs 预计机位」的复盘，不影响事前。

### 5.4 触发判据对比

| 编号 | 判据 | 稳定性 | 覆盖场景 | 取舍 |
|---|---|---|---|---|
| T1 | `eta_refined_min <= 30` | 中（会抖动） | 有遥测即可 | 主判据之一，但**不单独用** |
| T2 | `remaining_nm <= 150` | **高**（距离不会抖） | 有遥测即可，约等于 TOD | **主判据**，与 T1 取「先到者」 |
| T3 | `scheduled_arr_utc − 30min` | 高 | 没开模拟器/没开始录制也能提醒 | 仅作「计划提醒」，文案标明「按班期估算」 |
| T4 | 飞行阶段进入 `DESCENT/APPROACH` | 高 | 兜底（防止 T1/T2 都没中） | 兜底，延迟到进近才发也已可用 |

**已定（Q-1）**：`T2 或 T1 先到 → 发；T4 兜底；T3 只在没有遥测时用`。阈值全部进设置：`stand_lead_minutes`（默认 30，范围 10–60）、`stand_lead_nm`（默认 150，范围 60–300）。

### 5.5 去重、迟滞与边界

| 场景 | 规则 |
|---|---|
| 已通知后 ETA 又涨回 35 min | **不撤回、不重复**（`flight_stand.status=NOTIFIED` 即止） |
| 机位内容变化（补了场景库/冲突改派） | 允许第二条，`status=CHANGED`，文案「机位已变更：G340 → 532」 |
| 同一航班多段班表 | 每段独立，只对「当前在飞这一段」的 `arr_icao` 算 |
| 地速 <50 kt / 在地面 / 暂停 | 不触发（沿用 `flight_status` 的「不猜测」口径） |
| 模拟器时间加速 | 按模拟时间算，照常触发（结算侧已有 sim_rate 策略，这里不重复判罚） |
| 已经落地才开 AOC | 不发通知，只在执行页/日志里显示「实际到达机位」 |
| 无机位数据 | 仍可发「预计到达」提醒，但必须注明「该机场没有停机位数据」，**不编造编号**（同 `NAVDATA_MISSING` 口径） |

## 6. 方案 D：怎么把消息送到人

**硬约束**：前端 pulse 轮询在 `document.hidden` 时为 0 次（`App.tsx:251`）；执行页的 `/local/ops/flight-status` 2 s 轮询在隐藏标签页同样被节流。玩家在 MSFS 全屏时页面必然不可见 → **任何依赖页面定时器的方案都不可靠**。

| 编号 | 通道 | 覆盖形态 | 前置条件 | 可靠性 | 取舍 |
|---|---|---|---|---|---|
| N1 | 应用内通知（antd `notification` + 声音） | Tauri / 便携浏览器 | 页面可见 | 中 | **P1 必做底座**（回到页面能看到，可回溯） |
| N2a | Windows Toast via `tauri-plugin-notification`（**Rust 侧**轮询 `/local/notifications` 后弹） | 安装版 | 加插件 + capability `notification:default` + Rust 定时器 | **高**（与 webview 可见性无关） | **P2 推荐** |
| N2b | 便携版：`AOC-portable.exe` 托盘气泡（`Shell_NotifyIconW` + `NIF_INFO`） | 便携版 | 启动器要从「等健康检查一次」改成常驻轮询 | 高 | **P2 推荐**（字段已备好） |
| N2c | 浏览器 `window.Notification` | 便携版 | 一次性授权 + 页面可见 + 后台不被节流 | 低 | 不做（与 N2b 重复且更差） |
| N2d | Tauri **置顶迷你浮窗**（无边框，可叠在模拟器上） | 安装版 | 无（不碰模拟器接口） | 高（窗口化/无边框全屏下可见；独占全屏会被盖住） | **P2 做（Q-10），本地模式主通道**，见 §6.3.2 |
| N3 | 联机服务端：`SyncEvent(kind=stand.assigned)` 拉取，或 D-26/D-27 的 CPDLC 消息中心 | 联机 | 需要服务端调度 + 客户端常驻同步 | 中 | **P3**（先把事件 kind 定下来，别把机位塞进 CPDLC 报文语义） |
| N4 | Hoppie ACARS `telex` 直投机内（`COMPANY MSG` → MCDU `RECEIVED MESSAGES`） | 装了 Hoppie 客户端的机型 | 机组登入 Hoppie + 呼号严格一致 + 公司侧有站点 `logon` | 中（可达但无 ACK） | **P2.5 做（Q-2 ③），见 §6.1** |
| N5 | BeyondATC 自己的机位分配 | 用 BATC 的玩家 | BATC 已在分配；AOC 只能尝试**读**它的本地 WebSocket（未公开，V-9） | 高（它就是权威） | **让位（Q-7），见 §6.2** |

### 6.1 Hoppie / ACARS 能不能直接把机位推进飞机里

**能，而且就是本项目 D-26/D-27 已经写好的通道（尚未实现，见 11 §7.3）**。原理是：AOC 扮演「公司签派地面站」，把机位当成一条 **telex（自由文本）**报文发给机组呼号，机组的机载 ACARS 客户端自己轮询取回，ECAM 亮 `COMPANY MSG`，机组在 `MCDU MENU → ATSU → AOC MENU → RECEIVED MESSAGES` 里读。**不需要 CPDLC 连接**（CPDLC 是管制语义，且必须有在线 ATC 站配合，机位不是放行指令，不要用 `type=cpdlc`）。

接口与硬约束（据 Hoppie 官方 API 文档）：

```
POST http://www.hoppie.nl/acars/system/connect.html
  logon = <公司站点 logon code，≥24 字符，保密>
  from  = <公司签派站呼号，如 AOCDISP>
  to    = <机组呼号，必须与机上 FLT NO / Hoppie ID 完全一致>
  type  = telex
  packet= "AOC ARR GATE G340 JETWAY ETA 1842Z"   （大写、短、≤200 字符）
```

实测工具已就位：`tools/hoppie_telex.py`（纯标准库，不引依赖）。

```powershell
# 1) 先验 logon / 链路（type=ping，正常回 OK）
python -X utf8 tools/hoppie_telex.py --probe --logon gXXXX --from AOCDISP
# 2) 只看会发什么，不联网
python -X utf8 tools/hoppie_telex.py --dry-run --from AOCDISP --to AOC1234 --packet "AOC ARR GATE G340"
# 3) 真发（logon 也可用环境变量 HOPPIE_LOGON，避免进 shell 历史）
python -X utf8 tools/hoppie_telex.py --logon gXXXX --from AOCDISP --to AOC1234 --packet "AOC ARR GATE G340 JETWAY ETA 1842Z"
```

它会打印 HTTP 状态、响应原文与「判定（OK / REJECTED / UNKNOWN）」，并把每次发报写成 JSON Lines 追加到 `logs/hoppie-telex.log`（logon 一律打码、只留首尾各 2 位）；同时按 Hoppie 的要求自动保证两条报文间隔 ≥2 s，`--json` 便于脚本串联。**退出码**：`0` 正常、`2` 参数错、`3` 网络错、`4` 服务端错、`5` 被拒（如 `callsign already in use`）。

| 约束 | 内容 | 对本需求的影响 |
|---|---|---|
| 投递模型 | 存储转发 + 机组侧轮询；队列保留 **24 h** | 实测 A350 ≈30 s；即使出现 45–75 s 也属正常，可接受 |
| 机组轮询 | 地面/机载站约 **60 s 一次**（建议 45–75 s 随机），有预期消息时短时可到 20 s | **实测 iniBuilds A350 端到端约 30 s**（2026-11-06）；仍不承诺「秒达」 |
| 发送侧限流 | 发送无延迟要求，但**不要 2 s 内连发两条**；URL 建议 <256 字符，大载荷用 POST | 一个航段只发 1 条；换位通知也要排队 |
| 呼号锁 | `logon+callsign` 锁定 100 s；冲突返回 `callsign already in use` | 呼号写错**不会报错给机组**，只会静默躺 24 h → 必须有「呼号来源与校验」 |
| 回执 | **没有正式 ACK**；只能确认「已进网络」，不能确认「机组已读」 | 不能拿它当唯一通道（与 D-27 的降级一致） |
| 账号 | 每个飞行员需个人 Hoppie logon code（3 个月不用会失效）；**公司侧另需一个站点 logon code** 才有权按公司名义发报 | 密钥只能存服务端，绝不能进客户端/仓库 |
| 机型覆盖 | PMDG 737/777/747、Fenix A320（DCDU）、FlyByWire A32NX、iniBuilds A300/A310/A380、ToLiss、FSLabs；另有 EasyCPDLC / RealACARS 独立客户端 | 覆盖不少但**不是全部**，必须保留客户端通知兜底 |
| 服务性质 | 个人业余服务、无 SLA（2026-10 曾因安全漏洞下线数小时） | 失败必须静默降级，**绝不能阻塞航班流程** |

**设计结论**：

1. 通道优先级 = **Hoppie telex（机组在线且机型支持）→ 客户端系统通知（§6 的 N2a/N2b）→ 应用内消息**；
2. **触发在客户端、发送在服务端**：联机模式下服务端没有实时位置（11 §7.1：SimLink 事件尚未自动上报），所以由 `aoc-core` 判定 T-30，再 `POST /api/v1/flights/{id}/stand-notice` 请服务端代发 —— 公司 `logon` 只存在服务端，顺带天然限流与审计；
3. 报文状态机：`QUEUED → SENT → (EXPIRED / FAILED)`，`SENT` 只代表「已交网络」，界面文案写「已发送至 ACARS（回执未知）」，不写「已送达」；
4. 单发 vs 双发：D-27 原来定的是「同一报文只走一条」；**Q-6 已拍板破例** —— 机位属低风险信息类，**ACARS + 客户端镜像双发**（ACARS 为主），并在 `docs/README.md` 的 D-27 上注明这是例外。

### 6.2 BeyondATC：它自己就在分机位，别抢

BeyondATC（BATC）**已经实现了到达机位分配**：按呼号对应的真实机位、按机位实际使用频次挑、用真实翼展做占用冲突检查，并在落地后地面滑行许可里直接告诉机组「taxi to gate 25 via D, A1」。

所以关系不是「我们推给它」，而是：

| 场景 | 建议 |
|---|---|
| 玩家在用 BATC | **AOC 让位（Q-7）**：不通过 ACARS 推机位（否则机组会同时收到两个不同机位）；执行页标「由 BeyondATC 分配，请以地面许可为准」，不显示自己算的编号 |
| 玩家没用 BATC | AOC 自己按 §4 选位，并按 §6.1 走 Hoppie / 客户端通知 |
| 想拿到 BATC 分给谁 | BATC **有一个未公开的本地 WebSocket（默认端口 41716）**：社区桥接项目（`atc-network-bridge`）就是连它读 Status / Facility / Handoff 这类 JSON 消息。官方 wiki 没有把它当对外 API 写，schema 也没公开 → 只能算「可以尝试读」，**列为待验证 V-9**（§12） |

也就是说：**Hoppie 那条能「进飞机」，BATC 那条只能「让路」**；BATC 唯一能被本机程序借用的口子是它的 **ATIS 端点**（`localhost:57698`），而那是拉取不是推送，见 §6.3.1。两者同时启用时必须有一个权威方，建议「BATC 在线 → BATC 权威」。

### 6.3 本地模式能不能不走 Hoppie 也「进飞机」

两个问题分开答：**能不能冒充 BATC**、**本地模式是不是就不用第三方服务器**。

#### 6.3.1 冒充 BATC：确实有个口子（Fenix 的 ATIS），但实测不通、且是「拉」不是「推」 → **Q-11 决定不做**

> 本节保留完整取证，因为它是「为什么不做」的依据，也免得以后有人再走一遍。

**先纠一个之前的判断：不是完全够不着。** 同类项目 `japan-flight-dispatcher`（就在本仓库根目录，AOC 的 `docs/README.md` §5 也把它列为复用资产）已经把它做出来并跑了一个版本，实现见 `japan-flight-dispatcher/dispatcher/atis_server.py`：

```
Fenix A320 MCDU（NETWORK 选 BEYONDATC）
  → GET http://localhost:57698/acars/atis/<ICAO>        （黑盒实测，未公开接口）
  ← 200 + 纯文本  = 显示（24 列 × 7 行/页，`#` 显示不了）
  ← 404           = MCDU 显示 NO ATIS AVAILABLE
  ← 没有服务       = MCDU 显示 INVALID ATIS MESSAGE
```

也就是说：**BATC 的 ATIS 服务是跑在本机 57698 端口上的**，任何本机程序都能绑这个端口「冒充」它。该项目为此处理了三个坑（都值得照抄）：

| 坑 | 处理 | 出处 |
|---|---|---|
| Fenix 走 **IPv6 `::1`** | 同时绑 `127.0.0.1` 与 `::1`，缺 IPv6 才跳过 | `atis_server.py:78-100` |
| Windows 上端口抢绑检测不到 | `allow_reuse_address = False` | `atis_server.py:50` |
| 对方断开、请求很频繁 | `ConnectionError` 不刷日志；`protocol_version=HTTP/1.1` + `Content-Length` | `atis_server.py:22-31,53-56` |

**但这条口子的能力边界要说清**：

1. **只有 ATIS 页**。它是「机组按 MCDU 的 SEND → 服务端返回一份 ATIS」的拉取动作（该项目 `LiveService.text_for_sim` 的注释就是「MCDU 按 SEND = 请求最新 ATIS」），**没法在 T-30 主动推**。
2. **只有 Fenix**。PMDG/FBW/iniBuilds 各走各的（Hoppie 或自家 ACARS），别指望一套通吃。
3. **和真 BATC 抢同一个端口**。BATC 在跑时我们不能绑（对方的实现里绑失败会明确提示「端口 57698 无法使用」）—— 这恰好就是 §6.2「BATC 在线即让位」的具体落地方式。
4. **机位不是放行许可**。BATC 的机位是随地面滑行许可一起念出来的（`taxi to gate 25 via D, A1`），我们冒充它的 ATIS 只能给「信息」，不能、也不该去伪造管制指令。

**实测工具已就位**：`tools/batc_atis_sim.py`（纯标准库，默认就绑 57698）。

```powershell
python -X utf8 tools/batc_atis_sim.py --dry-run --stand G340      # 只看渲染（24 列 × 7 行）
python -X utf8 tools/batc_atis_sim.py --self-test                  # 自检 200/404/未知路径/抢端口
python -X utf8 tools/batc_atis_sim.py --stand G340                 # 起服务，Fenix 那边按 SEND
python -X utf8 tools/batc_atis_sim.py --icao ZBAA --stand G340 --once   # 只回 ZBAA、服务一次就退
```

它的日志会记下**每一个**打进来的请求（方法、路径、ICAO、状态码、字节数、来源地址、`Host`、`User-Agent`），所以它同时就是 V-13 的端点探针：把机组各页都点一遍，就能看清机型到底请求了哪些路径。端口被真 BATC 占用时它会直接拒绝启动并说明「应让位」；`--any-path` 让任何路径都回 200（机型换了路径也能看出来），30 s 没收到请求会主动提示。

> **实测结果（2026-11-06，本机）**
> - **Hoppie 投递：通** —— `tools/hoppie_telex.py` 发出，**iniBuilds A350 的 Mailbox 收到，端到端约 30 s**（2026-11-06）。
> - **BATC 通道：不通**。取证如下：
>   - 本机**没有安装 BeyondATC**（`%LOCALAPPDATA%` / `%APPDATA%` / `Program Files*` / `D:` / `E:` 下没有任何 beyond 目录）；
>   - Fenix 机模包 `D:\MSFS_2024\Community\fnx-aircraft-320*` 里**没有** `.wasm/.exe/.dll`，也没有 `BEYONDATC` 字样；
>   - Fenix 外部程序（`C:\Program Files\FenixSim A320\Fenix.exe`、`deps\FenixCDU.exe`、`deps\displays\FenixDisplay.exe`、`deps\systems\gateway\Fenix.GqlGateway.exe`、`%LOCALAPPDATA%\FenixApp\current\FenixApp.exe`）里**都有 `BeyondAtc` 字样**，但**没有任何一处出现 `57698` 或 `acars/atis`**（全盘扫到的 `57698` 是椭圆曲线十六进制常量里的片段，假阳性）。
> - 推论：**端口不是写死在 Fenix 的字符串里**，更可能是运行期由 BATC 侧启用/协商 —— 也就是「**没装 BATC 时 Fenix 根本不发这个请求**」。这与实测现象一致。
> - 处置：**通道 A 判不可用**（V-13 已关闭；Q-11 决定不做），单机按 D-2 走 Hoppie 或浮窗。

**对 AOC 的结论（Q-11 已定：不做）**：

- 本来可用的做法是把机位当成「ATIS 附加行」（机组按 SEND 查 ATIS 时末尾多一行 `ARR GATE G340`），零账号、零联网，但**要机组主动查、只覆盖 Fenix**；
- 2026-11-06 实测本机**连请求都收不到**（见上），叠加「拉取而非推送」「只覆盖 Fenix」「与真 BATC 抢端口」三条，**投入产出不划算 → 通道 A 正式关闭**；
- T-30 的主动提醒只走 Hoppie telex（§6.1）+ 客户端浮窗/系统通知（§6.3.2）。

> 另一条待挖：Fenix 在 `BEYONDATC` 网络下是否还有别的端点（`WX` / `PDC` / `FREE TEXT` / `RECEIVED MESSAGES`）。如果有，才算真正能「推」进 MCDU 的自由文本页 —— 列成 V-13，用抓包确认，别猜。

#### 6.3.2 本地模式：确实不用 Hoppie 的服务器，但也没有「免费进飞机」的捷径

Hoppie 的唯一作用是「把一段文本送到机载 ACARS 插件」——本地模式不需要它；但反过来，**MSFS 也没有给我们一个「在屏幕上写字」的可用接口**：

| 想法 | 实测/官方结论 | 可用性 |
|---|---|---|
| `SimConnect_Text`（滚动文本，FSX 时代的「绿条」） | 官方 SDK 原文：**deprecated and cannot be used in Microsoft Flight Simulator 2020**；社区实测它被绑到「飞行提示（Tips）」上，固定约 8 s，关掉 Tips 就什么都看不到 | **不可用**（2024 未单列，但同一套 API，不能靠它做功能） |
| 写进 MSFS 的 ATC 菜单 / 语音 | 无 API | 不做 |
| 本地迷你 Hoppie 服务器 | Hoppie 官网提到可跑本地迷你服务器做演示，但**机模插件把 `www.hoppie.nl` 写死**，除非改 hosts + 伪造证书 | 不可行 |
| **AOC 自己的置顶浮窗** | Tauri 已能开窗口，`always_on_top` + 无边框 + 透明是可配的；不碰模拟器接口 | **推荐（P2）** |
| **MSFS in-game panel**（SDK 的 HTML/JS 工具栏面板） | 这是唯一「真在模拟器里显示」且不依赖第三方的路；但要做 MSFS 包、分别验证 2020/2024 | P3 之后选做（工作量最大） |

所以本地模式的推荐组合是：**置顶迷你浮窗（主）+ 系统通知（副）+ 应用内记录（回看）**。浮窗可以拖到副屏或叠在模拟器右下角，不需要任何账号、不联网、不受机型限制。**注意**：按 Q-6 的双发口径，**浮窗始终镜像一份**（机内通道可用时也弹，玩家可在设置里关掉浮窗）；把「机内通道不可用」当作它唯一的场景已经过时。

**三种形态的最终通道矩阵**：

| 形态 | 主通道 | 兜底 | 备注 |
|---|---|---|---|
| 个人 / 单机运营（无 Hoppie） | Tauri 置顶浮窗 | 系统通知 → 应用内 | 全离线 |
| 单机运营（自愿配 Hoppie） | Hoppie telex（真进 MCDU） | 同上 | 需联网 + 个人 logon code；客户端**同时镜像一条**（Q-6 双发） |
| 联机（公司运行） | Hoppie telex（服务端代发） | 系统通知 → 应用内 | 公司站点 logon 只存服务端 |
| 玩家在用 BeyondATC | 不推机位，只标注 | 读回 BATC 结果（V-9） | 让位，避免两套指令 |

**统一投递模型**（无论哪个通道）：

```
aoc-core 判定触发 → 写 flight_notice 表（幂等：flight_record_id + kind）
                   → 暴露 GET /local/notifications?since=<ts>（轻量、游标）
Tauri（Rust 10 s）/ 便携启动器（10 s）/ 前端（可见时 2 s）各自拉取并各自弹
```

这样前端、Rust、启动器**共用一条队列**，谁在就谁弹，不会三处各写一套判定逻辑，也不会重复弹（`ack_by` 记谁消费过）。

### 6.4 单机模式的通道决策（**已定**，见 §13 D-1/D-2/D-3）

一句话：**能进机舱就进机舱；进不去就用浮窗，并且在界面上把「为什么是浮窗」写清楚。**

判据是两条都成立：

1. **这条路对当前机型可用**（不是「理论上存在」）；
2. **配置到位**（Hoppie 有 logon code / 网络在线）。

**2026-11-06 实测**：Pilot 侧用 `tools/hoppie_telex.py` 发 telex，**iniBuilds A350 的 Mailbox 收到，端到端约 30 s** → 通道 B 对 A350 成立（单机也走机内）。Fenix / FBW / PMDG 仍未实测（按同一机制预期可用，但不写进结论）。

| 通道 | 机型范围 | 推送还是拉取 | 前提 | 结论 |
|---|---|---|---|---|
| **A. 本地 BATC/ATIS 端点**（`localhost:57698`） | 仅 Fenix A320 | 拉取（按 SEND 才回） | 需真 BATC 存在 | **不做（Q-11）**：实测不通 + 拉取 + 只覆盖 Fenix |
| **B. Hoppie telex** | Fenix / iniBuilds A350（Mailbox）/ FBW / PMDG 等 | **推送** | 个人 logon code + 呼号一致 + 在线 | **做（Q-2 ③，P2.5）** |
| **C. AOC 浮窗 + 系统通知 + 应用内** | 全机型、全离线 | 推送（本地） | 无 | **做（Q-10，P2）**，兜底 |

> **关于 A350 的先验判断（待 V-14 实测确认）**：iniBuilds A350 的 CPDLC 是「通过 Hoppie 集成」的，官方特性表写的是 `ATIS/METAR requests` + `Mailbox functions`；社区实测反馈是「**即使只用 BeyondATC，也必须先填 Hoppie logon code**」（A350 EFB → Options → 3rd Party），MCDU 的 COM 页只是选网络。也就是说：**A350 走的是通道 B，不是通道 A**；它的本地 57698 端点大概率不存在。若 V-14 证明 telex 能进它的 Mailbox，那 A350 反而比 Fenix 更适合推送（真·机内、主动）。

**降级必须写明原因**，不能静默。原因码与文案：

| 原因码 | 界面文案（执行页机位卡 / 浮窗脚注） |
|---|---|
| `TYPE_UNSUPPORTED` | 本机型未提供 AOC 机内消息通道，已在 AOC 浮窗显示 |
| `HOPPIE_NOT_CONFIGURED` | 未配置 Hoppie logon code（设置 → 到达提醒），已改用浮窗 |
| `HOPPIE_OFFLINE` | Hoppie 不可达（或呼号与机上不一致），已改用浮窗 |
| `BATC_AUTHORITATIVE` | BeyondATC 正在运行，机位以它的地面许可为准 |
| `NO_STAND_DATA` | 该机场没有停机位数据，只提供预计到达时刻 |

设置页同时给一张「机型支持矩阵」（下表）与「当前生效通道」，玩家能自己判断是配置问题还是机型问题。

| 机型 | 通道 A（本地 ATIS） | 通道 B（Hoppie） | 状态 |
|---|---|---|---|
| Fenix A320 | ❌ 不做（Q-11；实测也不通） | ✅ DCDU / RECEIVED MESSAGES | **B 待实测** |
| iniBuilds A350 | ❌ 不适用（它只认 Hoppie） | ✅ **已实测（2026-11-06）：Mailbox 收到，端到端约 30 s** | **通道 B 可用**，单机即走机内 |
| FlyByWire A32NX | ❌ | ✅ ACARS / TELEX | B 待实测 |
| PMDG 737/777/747 | ❌ | ✅ ACARS | B 待实测 |
| 其他 / 默认 | ❌ | ❌ | 走通道 C |

## 7. 数据模型与接口（建议稿）

### 7.1 新表（`packages/aoc_core/aoc_core/ops/schema.py`）

```sql
-- 预计/实际停机位（一段航班一条；改派留 before/after 到 ops_audit）
CREATE TABLE IF NOT EXISTS flight_stand (
    flight_record_id TEXT PRIMARY KEY,
    airport_icao     TEXT NOT NULL,
    stand_ident      TEXT,              -- 展示名：G340
    stand_name TEXT, stand_number INTEGER, stand_suffix TEXT,   -- 原始三段
    stand_type       TEXT,              -- GS/GM/GH/GE/RC/...
    lat REAL, lon REAL, heading REAL, radius_m REAL, has_jetway INTEGER,
    source           TEXT NOT NULL,      -- override/scenery/navdata/learned/none
    score_json       TEXT,               -- 打分明细（可解释性/排障）
    status           TEXT NOT NULL DEFAULT 'PROPOSED', -- PROPOSED/NOTIFIED/CHANGED/CONFIRMED
    eta_min_at_pick  REAL, remaining_nm_at_pick REAL,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL
);

-- 到机位的真实样本（落地/收尾时写），用于校验场景库编号 + 给无机位机场补候选
CREATE TABLE IF NOT EXISTS stand_sample (
    id TEXT PRIMARY KEY,
    airport_icao TEXT NOT NULL, lat REAL NOT NULL, lon REAL NOT NULL,
    heading REAL, stand_ident TEXT,        -- 与场景库最近位（≤80 m）匹配成功时回填
    flight_record_id TEXT, created_at TEXT NOT NULL
);

-- 手工覆盖（与 airport_runway_override 同模式）
CREATE TABLE IF NOT EXISTS airport_stand_override (
    icao TEXT NOT NULL, stand_ident TEXT NOT NULL,
    lat REAL NOT NULL, lon REAL NOT NULL, heading REAL, radius_m REAL,
    has_jetway INTEGER, note TEXT, updated_at TEXT NOT NULL,
    PRIMARY KEY (icao, stand_ident)
);

-- 通知收件箱（多消费者共用一条队列，见 §6）
CREATE TABLE IF NOT EXISTS flight_notice (
    id TEXT PRIMARY KEY, kind TEXT NOT NULL,          -- STAND_ETA / STAND_CHANGED / ETA_ONLY
    flight_record_id TEXT, airport_icao TEXT, title TEXT NOT NULL, body TEXT NOT NULL,
    payload_json TEXT, created_at TEXT NOT NULL,
    ack_by TEXT, ack_at TEXT,
    UNIQUE (flight_record_id, kind)
);
```

另有 §4.5 的 `airport_terminal` / `terminal_rule` 两张表（航站楼事实与承运人规则），以及两个新列：`flight_stand.terminal` / `terminal_source`、`ops_profile.airline_codes`（公司承运人代码，逗号分隔多值）。
